# SOP: Adding a Time Dimension to Your Personal Knowledge Base
# SOP：给一个个人知识库加上「时间」维度

> **Goal / 目标**：make retrieval time-aware, with "newer beats older" adjustable, explainable and testable.
> Stdlib only. Every step has an acceptance criterion — don't move on until it passes.
> 让检索结果自带时间，且「新资料压过旧资料」这件事可调、可解释、可验证。全程只用 Python 标准库，
> 每一步都有验收标准，不通过就别往下走。

---

## 第 0 步：先确认你真的需要时间项（10 分钟）

**验收标准**：同一批问题，开/关时间项的结果差异 ≥ 2/10 才算值得做。

```bash
python decay_rag.py build <语料目录> --index idx.json
python decay_rag.py query "你最关心的前 10 个问题之一" --index idx.json
python decay_rag.py query "同一个问题" --index idx.json --no-decay
```

如果两个结果一模一样，先别做时间项——你的语料要么很新，要么问题根本不关心时效。
个人助理、长期陪伴、制度类知识库通常值得做；一次性文档集通常不值得。

---

## 第 1 步：定语料范围（决定后面所有事）

- 只放**你会问**的东西。语料越杂，检索越差，时间项越救不回来。
- 排除索引文件、构建产物、大二进制。
- 记住一个事实：语料里如果混着「当初的方案」和「现在的方案」，才有时间项的用武之地。

**验收**：列得出「这个库里哪些结论已经过期了」至少 3 条。

---

## 第 2 步：切块（决定了后面能不能定位到「哪一句话过期了」）

默认 `700 字 / 重叠 120 字`，按空行分段，单段超长硬切。

- 块太大：一块里混着新结论和旧结论，时间戳只能取一个，必然错。
- 块太小：上下文断裂，语义检索退化。
- **验收**：随机抽 5 块，人眼判断「这一块里的信息是不是同一个时间写的」。有一条不合格就调小 `CHUNK_SIZE`。

---

## 第 3 步：块级时间戳（本项目核心，别跳过）

`parse_chunk_ts()` 的优先级：

1. **文件名里的日期** —— `复盘_2026-03-31.md` → `2026-03-31`。最可靠，建议所有文件都带。
2. **块内离文件 mtime 最近的日期** —— 不是「第一个日期」。
3. `10-31` 这类简写（年份取当年，算出来比现在晚 30 天以上就退一年）。
4. 兜底：文件 mtime。

**为什么第 2 条不是「第一个日期」**：回测报告正文常这么写——

```
回测区间 2019-01-02 至 2025-12-31，结论：……
```

取第一个日期，整块会被标成 2019 年，衰减算成 `0.00`，这块永远排不上来。
文档的写作时间总是贴近 mtime，正文里的历史日期离得远 → 所以挑**最近的**。

**验收**：

```python
python -c "from decay_rag import parse_chunk_ts; print(parse_chunk_ts(open('data/sample/审计档案_2026-11-09.md',encoding='utf-8').read(),'data/sample/审计档案_2026-11-09.md'))"
```

打印出来必须是 `2026-11-09` 附近，不是 2019。

---

## 第 4 步：打分

```
相似度 = W_COS×余弦 + W_LEX×字面重合      # 0.72 / 0.28
衰减   = 0.5 ** (块龄 / 半衰期)
综合分 = W_SIM×相似度 + W_TIME×衰减        # 0.75 / 0.25
```

- `字面重合` 是「查询里的二元组有多少在块里出现」，长文档不吃亏（召回向）。
- 余弦用字符 2/3-gram 稀疏计数；要换真嵌入模型，只需把 `ngram_counts` 换成 embedding 调用，
  其余打分逻辑一行不用改。

**验收**：构造两个内容相同、时间不同的块，确认新的排在前面（`tests/test_decay.py::test_equal_content_newer_wins`）。

---

## 第 5 步：调半衰期（唯一需要凭感觉的参数）

| 语料 | 建议半衰期 | 理由 |
|---|---|---|
| 个人笔记 / 日记 | 30 天 | 一周前的东西通常还有效 |
| 实时情报 / 告警 | 1–3 天 | 过期即噪音 |
| 制度 / 法规 / 教科书 | 365 天以上 | 时效性弱，但改版后旧版必须沉下去 |
| 项目交接文档 | 14 天 | 一周内的决定最有价值 |

方法：固定 10 道题，扫 `--half-life 1/3/7/30/90`，看**你认可的那一条**排第几。
不要优化平均值，优化「最差的那条」——时间项调坏了，通常是某类问题集体沉底。

---

## 第 6 步：验证（写出对照表，别凭感觉）

```bash
for hl in 1 3 7 30 90; do python decay_rag.py query "<你的问题>" --index idx.json --half-life $hl; done
```

**验收标准**：

- 至少 1 道题因为时间项从「错」变「对」；
- 没有题目因为时间项从「对」变「错」。

两条都满足才算能用。只满足第一条，说明权重给大了；都不满足，说明你的语料没有时效冲突。

---

## 第 7 步：上线与维护

- 每次增量更新后重建索引；语料 < 1 万块时全量重建比增量省心（千块级全量重建约 1 秒）。
- **检索时永远把时间戳打印出来**。用户一旦看见「这条是 2019 年的」，就不会被过时结论骗。
- 每季度重跑一次第 6 步的对照表，语料结构变了，半衰期该跟着变。

---

## 常见翻车（本项目都踩过）

| 现象 | 原因 | 修法 |
|---|---|---|
| 衰减开了等于没开，所有块「0 天」 | 用的是文件 mtime，语料是单文件写到底 | 下沉到块级时间戳 |
| 某些块永远是 0.00 | 正文历史日期被当成写作日期 | 取离 mtime 最近的日期 |
| 新结论排不上来 | 旧文档更长、更像 | 加 `--current-only`；或把旧文档移出索引 |
| 同义词查不到 | 字面余弦的天然短板 | 查询扩展，或换嵌入模型（此时只替换 `ngram_counts`） |
| 数字问题答错 | 向量检索不适合精确数值 | 数字走结构化查询，别硬套 RAG |
